# Codex plan for mehrangta/telegram_project_manager#28

Job: `c-5ffe1e81` · Revision: 1

Implement a new admin-only `/brainstorm` workflow that inspects the active repository through the existing Codex SDK and detached-worktree infrastructure, returns exactly three evidence-backed improvement suggestions, and optionally runs on a durable per-repository schedule. The draft assumes the recommended answers below: one schedule and Telegram destination per repository, interval presets anchored to an explicit UTC time, and a repository feature toggle that gates both manual and scheduled runs while preserving schedule configuration. Existing repositories remain disabled by default, so rollout is backward-compatible and requires explicit admin enablement.

## Risks

- The shared Codex adapter currently uses `Sandbox.full_access`; read-only behavior is enforced by instructions and a disposable detached worktree rather than an OS sandbox. The new prompt must retain all existing secret and mutation restrictions, and documentation must not imply stronger isolation.
- A repository-global destination means enabling the same repository from another chat/topic moves scheduled delivery. This must be explicit in command responses and documentation to avoid surprising administrators.
- If multiple main bot processes point at the same SQLite database, scheduler polling can duplicate work unless due-run claiming is performed atomically in SQLite. Avoid relying only on in-memory locks.
- Telegram destinations can become invalid because the bot is removed, blocked, or loses topic permissions. Treat these as failed occurrences, sanitize and audit the provider error, retain configuration, and wait until the next scheduled occurrence.
- Local cache paths and branches are currently scope configuration rather than global repository metadata. Persist the selected path and branch with the brainstorm configuration and validate them on every run so later scope changes cannot silently analyze the wrong checkout.
- Codex analysis can run for up to the existing multi-hour timeout and consume substantial provider capacity. A low concurrency limit, duplicate suppression, queue visibility, bounded output, and no immediate automatic retries are necessary.
- Interval scheduling anchored to UTC avoids daylight-saving ambiguity but may not match an administrator's local wall-clock expectation. If local time zones are required, the parser, schema, display, and DST tests become more complex.
- Suggestions may repeat across scheduled runs because the issue requests repository inspection, not recommendation history or deduplication. Do not add long-term suggestion memory unless explicitly requested.
