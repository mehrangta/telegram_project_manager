# Codex plan for mehrangta/telegram_project_manager#28

Job: `c-5ffe1e81` · Revision: 2

Implement the existing `bots/ideas` placeholder as an admin-only `/brainstorm` feature. A manual run inspects the active repository with the existing Codex plan model and detached-worktree flow, then returns exactly three ranked, evidence-backed improvements. Brainstorming is a repository-global feature flag: when disabled, both manual and scheduled runs are rejected, while schedule settings remain stored. Each repository has one scheduled Telegram destination; `/repo brainstorm enable owner/repository` records or moves that destination to the invoking chat/topic. Scheduling uses dependency-free interval presets (`daily`, `2d`, `weekly`, or `Nd`) at an explicit UTC `HH:MM`. Existing repositories default to disabled, and no existing command behavior changes.

## Risks

- Codex currently runs with `Sandbox.full_access`; read-only behavior is provided by instructions and a disposable detached worktree, not OS-enforced isolation. The prompt and documentation must preserve the existing warnings about filesystem, network, and secret exposure.
- Each repository has exactly one scheduled destination. Enabling it from a different chat or topic intentionally moves future delivery, so confirmation and `show` output must identify the destination clearly.
- A scheduled occurrence is advanced when atomically claimed to prevent duplicate posts across bot processes. A crash after claim can therefore skip that occurrence; exactly-once delivery cannot be guaranteed across SQLite and Telegram without a more complex outbox protocol.
- The repository branch and cache used by scheduled runs are snapshots from the most recent enable operation. They are revalidated on every run, but later `/branch` or `/repo local set` changes do not affect the schedule until an admin enables the repository again from that scope.
- UTC-only wall-clock scheduling avoids timezone and daylight-saving ambiguity but requires administrators to convert from local time. Responses and documentation must always include `UTC`.
- Long Codex inspections can consume significant provider capacity. A concurrency limit of one, queue limit, repository-level claim, bounded response, and no immediate retry reduce cost and duplicate analysis.
- Disabling brainstorming prevents both new manual and scheduled runs but intentionally lets an already-running job finish and deliver its snapshotted result; this behavior must be explicit to avoid treating disable as cancellation.
- Recommendations may repeat between scheduled runs because no recommendation history or deduplication store is required. Adding semantic history would introduce product behavior beyond this issue.
