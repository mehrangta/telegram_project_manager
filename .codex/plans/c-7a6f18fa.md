## Risks

- The CLI parser, Telegram handlers, in-bot `/help`, and README currently duplicate command metadata and can drift again; this issue should explicitly treat the parser and handlers as authoritative and avoid claiming `/help` is exhaustive.
- An exhaustive flat list could make onboarding harder; retain the existing quick-start and group the reference by CLI, repository administration, issues, Codex jobs, and merge/deployment workflows.
- `/confirm` and `/cancel` serve both issue drafts and direct commit plans, while `/edit` and `/code edit` manage different resources; unclear grouping could cause users to supply the wrong identifier type.
- Some accepted configuration keys have limited validation, and `require_confirmation` is accepted but has no current runtime read path; document it only as an accepted compatibility setting rather than promising behavior not present in the code.
- Several commands depend on contextual state—registered admin identity, private chat, active and allowed repository, exact forum topic, local cache, enabled brainstorming, or deployment configuration—so syntax-only documentation could still be misleading unless these prerequisites are stated.
- No Markdown linter or automated README-to-handler consistency test is configured, so completeness requires a deliberate manual inventory check in addition to the existing unit suite.
