# Codex plan for mehrangta/telegram_project_manager#51

Job: `c-10ee1898` · Revision: 1

Add a best-effort, five-second completion notification for successful manual `/brainstorm` runs. The notification is a new Telegram message because manual results currently replace the queued message via edit, which may not produce a fresh client notification. Scheduled runs already send a new result and remain unchanged. No database, schema, command, or public Telegram API changes are required.

## Steps

1. **Define manual completion behavior** — In `BrainstormService`, add a default five-second completion-notice duration, injectable through the keyword-only constructor for deterministic tests. After the final brainstorm result has been successfully delivered and only when `trigger == "manual"`, send a separate `✅ Repository brainstorm complete.` message to the same chat and forum topic. Do not attach it as a reply, delete or replace the final brainstorm result, emit it for scheduled runs, or emit it for failed or cancelled runs.
   - Likely files: `src/telegram_project_manager/bots/ideas/service.py`
2. **Schedule best-effort deletion** — Capture the completion message ID returned by the existing `_send` path, then start a tracked asynchronous task that sleeps for the configured duration and calls the existing `TelegramBotApi.delete_message(chat_id, message_id)`. Keep notification send and deletion failures non-terminal: log them without changing an otherwise successful brainstorm status, audit result, cleanup, or queue state. Treat Telegram's message-not-found response as an already-completed deletion rather than a warning.
   - Likely files: `src/telegram_project_manager/bots/ideas/service.py`, `src/telegram_project_manager/platform/telegram_bot.py`
3. **Manage notification task lifecycle** — Store delayed-deletion tasks separately from brainstorm execution tasks so the five-second timer does not keep a completed brainstorm in `_tasks`, consume a queue slot, delay database completion, or block subsequent work. Remove finished tasks through a done callback that consumes unexpected exceptions. During `shutdown`, cancel pending timers, have their cancellation path attempt immediate deletion of any already-sent notification, and gather the tasks so shutdown does not leak background work or leave avoidable notices behind.
   - Likely files: `src/telegram_project_manager/bots/ideas/service.py`
4. **Extend brainstorm service tests** — Enhance `FakeBot` with deletion recording and configurable send/delete failures, and construct the service with a zero-duration notice in normal tests. Update the manual-success test to verify the final result still edits the queued message, a second message with the completion text is sent to the same chat/topic, and only that second message is deleted. Preserve assertions that scheduled success sends only its permanent result and that failure, over-budget, edit-failure, and cancellation paths do not send completion notices. Add focused coverage proving completion-message send or deletion failure does not convert a successful brainstorm to failed, and that shutdown immediately cleans up a pending notice timer.
   - Likely files: `tests/test_brainstorm.py`
5. **Document delivery semantics** — Update the ideas-bot documentation to state that successful manual runs retain their edited result and additionally send a transient five-second completion notice, while scheduled runs continue to post only their terminal result. No configuration key or migration is introduced; deployment requires only the normal service restart.
   - Likely files: `src/telegram_project_manager/bots/ideas/README.md`
6. **Validate targeted and full behavior** — Run the brainstorm test module first, then the complete unittest suite in the repository's documented `uv` environment. Confirm manual and scheduled success paths, failure/cancellation compatibility, delayed deletion, shutdown cleanup, and absence of database migration changes. The planning environment did not have `uv` installed, so these commands were identified but could not be executed during inspection.
   - Likely files: `tests/test_brainstorm.py`, `pyproject.toml`

## Validation

- `TPM_TEST_CODEX_STUBS=1 uv run python -m unittest discover -s tests -p 'test_brainstorm.py'`
- `TPM_TEST_CODEX_STUBS=1 uv run python -m unittest discover -s tests`
- Manual success: queued message becomes the permanent result; a new completion notice is sent in the same chat/topic and deleted after the configured delay.
- Scheduled success: the result remains a single newly sent permanent message with no redundant completion notice or deletion.
- Failure and cancellation: existing terminal messages remain unchanged and no success notification is emitted.
- Notification API failures: send/delete errors are logged but do not alter the successful brainstorm database status or remove the final result.
- Shutdown: pending delayed-deletion tasks are drained and their already-sent notices are deleted immediately.

## Risks

- Telegram deletion is best-effort: insufficient bot permissions, Telegram API errors, or a user deleting the message first can prevent or supersede cleanup; these cases must not fail the brainstorm.
- A process crash between sending and deleting the notice can leave it behind because the timer and message ID are intentionally in memory rather than persisted; adding persistence would be disproportionate for a five-second notification.
- A fresh Telegram message can trigger normal client notification behavior, but audible or push alerts still depend on each user's Telegram mute and notification settings.
- Background timing tests can become flaky unless the delay is injected and tests explicitly await tracked notification tasks rather than sleeping for wall-clock time.
