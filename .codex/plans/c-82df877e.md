# Codex plan for mehrangta/telegram_project_manager#67

Job: `c-82df877e` · Revision: 1

Enhance `/issues` so each open GitHub issue shows the status of its newest locally persisted Codex code job, when one exists. Resolve statuses by repository and issue number in one SQLite query, display the raw canonical status in human-readable form, and reuse the existing 60-second issue-list refresh and render-hash mechanism so tracked Telegram messages update automatically. Include terminal states such as `ready` and `discarded`; omit the Codex label for issues that have never had a code job. No configuration, GitHub API, command-routing, or database-schema migration is required.

## Risks

- Status changes are eventually consistent in `/issues`: background messages may lag the `code_jobs` table by up to the existing 60-second refresh interval. The initial `/issues` response remains immediate.
- A repository can have multiple terminal jobs for one issue. Selection must be based primarily on job creation time, not only `updated_at`, or later deployment activity on an older ready job could hide a newer attempt.
- Adding status text increases Telegram message length. Keep the status on the existing issue-title line and test a full 20-item response; the implementation should not change the current issue limit, keyboard ordering, or command visibility as part of this issue.
- The status lookup must remain a single batched query. Calling `get_active_code_job()` for every issue would introduce repeated SQLite connections, omit `ready` and `discarded` states, and make periodic refresh cost grow with the issue-list size.
- The issue list reflects only code jobs known to this bot's local SQLite database. Codex or automation activity created outside this installation cannot be inferred from GitHub and should not be presented as known status.
