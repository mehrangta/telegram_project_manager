# Codex plan for mehrangta/telegram_project_manager#30

Job: `c-c51f1b87` · Revision: 1

Implement `/brainstorm` repository auto-detection from the existing per-repository brainstorm destination stored in `brainstorm_configs` (`telegram_chat_id` plus exact `telegram_thread_id`). Do not infer from Telegram chat titles or topic names: those values are not carried through `IncomingMessage`, while the persisted destination is already the repository-aware interface used by scheduled brainstorms. Preserve the current active-repository path as a compatibility fallback when no brainstorm configuration targets the command’s exact scope.

## Steps

1. **Add exact-scope configuration lookup** — Add a `Database` query such as `list_brainstorm_configs_for_scope(chat_id, thread_id)` that returns brainstorm configurations assigned to the exact Telegram destination, ordered by repository for deterministic handling. Match chat commands only to rows where `telegram_thread_id IS NULL`; match topic commands only to the same `telegram_chat_id` and identical non-null thread ID. Do not inherit chat-level destinations into topics. Add an idempotent index on destination columns, for example `(telegram_chat_id, telegram_thread_id, enabled, repo)`, through `Database.initialize()` so existing databases receive it without a schema-version migration.

## Risks

- `brainstorm_configs` currently permits several repositories to share one destination. Automatic detection must explicitly handle this rather than silently choosing by database order.
- Destination configuration stores a branch and local cache snapshot from enablement time. That data can become stale; existing workspace validation should remain the failure boundary instead of falling back to metadata from a different repository.
- SQLite null comparisons can accidentally make chat-level rows match topics or vice versa. The lookup must use explicit `IS NULL` handling and exact non-null thread equality.
- Choosing a sole destination mapping over an unrelated active repository changes `/brainstorm` precedence, but confines the change to this command and fulfills destination-based auto-detection; other repository-aware commands remain unchanged.
- Disabled configurations preserve destinations, so stale rows may contribute to ambiguity. The resolver and error text must distinguish enabled candidates and allow an explicitly active matching repository to disambiguate.
- Adding a non-unique index is safe for existing data, while adding a uniqueness constraint would not be: current behavior allows multiple repositories to publish scheduled brainstorms to the same chat or topic.
