# Codex plan for mehrangta/telegram_project_manager#34

Job: `c-417af34d` · Revision: 1

Change manual `/brainstorm` repository resolution to consistently use the exact chat or forum topic’s active/default repository, matching `/ask`, `/do`, and other repository-aware commands. Keep per-repository brainstorm enablement, schedules, and configured scheduled destinations intact; only manual selection precedence changes. No database migration or product clarification is required.

## Steps

1. **Use Exact Scope Repository** — In `BrainstormManager._resolve_manual_repository`, load `Database.get_scope_settings(message.chat_id, message.thread_id)` and select only its `active_repo`. Return the existing reply-linked “No active repo for this chat/topic” response when unset. Remove destination-config lookup, enabled-config candidate selection, and ambiguity handling from this manual resolution path. Delete `_ambiguous_repository` if it becomes unused. Preserve exact topic isolation: a topic without settings must not inherit its parent chat’s repository.
   - Likely files: `src/telegram_project_manager/bots/ideas/commands.py`
2. **Preserve Current Scope Metadata** — Continue passing the active scope’s current `default_branch` and `local_repo_path` into `BrainstormService.submit`, falling back to `main` and an empty path exactly as today. Do not source branch or cache values from `brainstorm_configs`, because those fields are snapshots for scheduled execution and may be stale after `/repo set`, `/branch`, or cache configuration changes.
   - Likely files: `src/telegram_project_manager/bots/ideas/commands.py`
3. **Retain Eligibility Checks** — After selecting the scope’s active repo, preserve the current validation order and responses: reject repositories outside `allowed_repos`; load that repo’s `brainstorm_configs` row; reject missing or disabled configuration with `/repo brainstorm enable <repo>` guidance; then submit the manual run and retain existing handling for repository, workspace, value, and Telegram API failures. Do not silently switch to another enabled repo configured for the same destination.
   - Likely files: `src/telegram_project_manager/bots/ideas/commands.py`
4. **Leave Scheduling Unchanged** — Do not change the `brainstorm_configs` schema, destination fields, destination index, schedule configuration commands, enable/disable behavior, due-run claiming, recovery, or scheduled delivery. Existing configured destinations must continue determining where scheduled brainstorm results are sent. No migration or backfill is needed, and saved schedules remain valid across rollout.
   - Likely files: `src/telegram_project_manager/platform/storage/db.py`, `src/telegram_project_manager/bots/ideas/service.py`
5. **Replace Resolver Regressions** — Update manager tests that currently assert destination auto-detection. Cover that the active chat/topic repo wins when another repo is configured for that destination; current scope branch and cache values win over stale brainstorm-config snapshots; no active repo returns the existing chat/topic-specific error even when one or more destination configs exist; a disabled active repo is rejected rather than falling through to another enabled repo; and topics still do not inherit chat defaults. Retain coverage for allowed-repo checks, enabled configuration, command mentions, reply IDs, and successful submission arguments.
   - Likely files: `tests/test_brainstorm.py`
6. **Clarify Manual Versus Scheduled Behavior** — Update user-facing documentation to state that manual `/brainstorm` always uses the exact chat/topic active repository, while scheduled runs continue using the destination saved by `/repo brainstorm enable`. Remove claims that manual runs auto-detect destination-bound repositories or use the active repo only for disambiguation and fallback. Keep command syntax unchanged.
   - Likely files: `README.md`, `src/telegram_project_manager/bots/ideas/README.md`
7. **Validate And Roll Out** — Run the focused brainstorm suite first, then the full unittest suite. Verify no database migration is generated and no public command syntax changes. Roll out through the normal application deployment/restart; existing database rows remain compatible. After deployment, manual runs in scopes without an active repo will intentionally require `/repo set owner/repository`, even if that scope is a saved scheduled destination.
   - Likely files: `tests/test_brainstorm.py`, `src/telegram_project_manager/bots/ideas/commands.py`

## Risks

- This intentionally breaks reliance on destination auto-detection for manual runs; affected chats/topics must have an active repo configured with `/repo set`.
- A destination may continue receiving scheduled results for repo B while manual `/brainstorm` in that same scope runs repo A; documentation must clearly distinguish these independent behaviors.
- The active repo must itself have brainstorming enabled. Falling back to another enabled destination repo would contradict the issue and must not be retained.
- Using current scope branch and cache values can surface existing invalid or missing cache configuration immediately; preserve current error handling rather than reverting to stale scheduled snapshots.
- Removing or migrating destination columns, indexes, or stored configurations would create unnecessary compatibility risk and is outside this issue’s scope.
