# Codex plan for mehrangta/telegram_project_manager#69

Job: `c-c10f3710` · Revision: 1

Issue-draft creation fails when the LLM emits a plain-text title instead of the required JSON object. The failure blocks draft creation and exposes LangChain’s low-level structured-output parsing message to the Telegram user. Address the contradictory title prompt and extend the shared structured-output client’s existing single-repair path to recover from explicit parsing errors as well as missing parsed objects, without changing issue-body policy or persistence formats.

## Steps

1. **Make title prompts schema-explicit** — Update both title creation and title revision prompts to request exactly one JSON object containing a non-empty `title` string, rather than saying “Return the title only.” Keep the existing instructions to preserve user intent, leave the original issue body unchanged in title-only mode, and avoid invented details. This removes the prompt/schema contradiction that can produce the reported plain-text title while retaining `ISSUE_TITLE_RESPONSE_SCHEMA` as the public contract passed by `IssuePlanner`.
   - Likely files: `src/telegram_project_manager/bots/issue_manager/prompts.py`
2. **Repair structured parsing errors once** — Refactor `OpenAICompatibleClient.chat_json` so a valid response wrapper with either a non-null `parsing_error` or no recoverable parsed object enters one shared repair path. Build the repair conversation from the original invocation messages, include the first raw `AIMessage` when available so the corrective instruction has the actual failed response, append the existing schema-guided instruction, and invoke the base `ChatOpenAI` model once. Parse the repaired message with the existing raw-message JSON-object helper and return it through the normal success path. Do not retry transport/provider exceptions, malformed non-dictionary response wrappers, or recursively repair a failed repair; this keeps retries bounded and avoids duplicate draft generation.
   - Likely files: `src/telegram_project_manager/platform/llm/client.py`
3. **Preserve validation and persistence behavior** — Leave the `chat_json` interface, JSON schemas, `IssuePlanner` calls, and database records unchanged. Successful initial responses must incur no additional request. Successful repairs must flow into the existing `IssueDraft` or commit-plan validation, so required fields, title length, allowed repository paths, and body-mode rules remain authoritative. With LLM body generation disabled, continue storing the user’s request verbatim as `raw_body` and using only the repaired `title`; generated-body creation and both revision paths should receive the same shared resilience automatically. When memory is enabled, persist only the original user request and the successful repaired JSON response, never the invalid first response. If the repair request raises, continue wrapping it as `LlmError`; if it
   - Likely files: `src/telegram_project_manager/platform/llm/client.py`, `src/telegram_project_manager/bots/issue_manager/planner.py`, `src/telegram_project_manager/bots/issue_manager/schemas.py`
4. **Add focused regression coverage** — Replace the current expectation that a structured `parsing_error` is never retried with a regression reproducing the issue: the structured call returns raw plain text such as `Add economic news execution guard to trade preflight` plus a JSON parsing error, the repair call returns `{"title":"Add economic news execution guard to trade preflight"}`, and `chat_json` returns the title object. Assert exactly one structured call and one repair call, verify that the repair messages include the original request, failed AI output, schema, and no-markdown instruction, and cover an unparseable repair producing the stable terminal `LlmError`. Retain coverage for recovering JSON from raw metadata/content, missing parsed objects, provider exceptions, invalid response wrapper types, caller-supplied schema
   - Likely files: `tests/test_llm_client.py`
5. **Cover issue title-only workflows** — Extend the existing issue-planner tests for `issue_body_llm_enabled=false` and original-body revisions to assert that both prompts explicitly request a JSON object with a `title` field and still pass `ISSUE_TITLE_RESPONSE_SCHEMA`. Verify draft creation continues to skip repository-context collection and LLM memory in title-only mode, preserves the exact raw issue body, stores a pending draft only after title validation succeeds, and leaves original-body revisions unchanged except for the title.
   - Likely files: `tests/test_repository_context.py`, `src/telegram_project_manager/bots/issue_manager/prompts.py`
6. **Validate and roll out safely** — Run the focused unittest modules first with `PYTHONDONTWRITEBYTECODE=1 uv run python -m unittest tests.test_llm_client tests.test_repository_context tests.test_issue_manager`, then run the complete suite with `PYTHONDONTWRITEBYTECODE=1 uv run python -m unittest discover -s tests`. No schema migration, configuration change, or backfill is required. Deploy through the existing application process and monitor existing `issue.plan` failed audit records for residual structured-output failures; rollback is limited to the client and prompt changes because stored draft and configuration formats remain compatible.
   - Likely files: `pyproject.toml`, `tests/test_llm_client.py`, `tests/test_repository_context.py`, `tests/test_issue_manager.py`, `src/telegram_project_manager/bots/issue_manager/commands.py`

## Validation

- A plain-text title accompanied by LangChain `parsing_error` is corrected into the schema-required title object and allows issue-draft creation to continue.
- A missing parsed object with raw `null` still receives exactly one repair attempt and succeeds when the repair returns a JSON object.
- An invalid repair result such as empty text, `null`, an array, or non-JSON fails after one repair with a stable high-level `LlmError` and does not loop.
- Transport/provider exceptions and malformed non-dictionary structured response wrappers retain their existing immediate failure behavior.
- Successful structured responses make no repair request.
- Persistent LLM memory stores only the successful repaired JSON response and replays it on the next request.
- Title-only draft creation preserves the request body verbatim, skips repository context and memory, and passes the title schema.
- Original-body revision changes only the title and continues to skip repository context collection.

## Risks

- The repair path adds one additional model request, latency, and token cost only when the first structured response is unusable.
- Because `chat_json` is shared with direct-commit planning, changing parsing-error recovery affects all structured LLM callers; full-suite coverage is needed to ensure downstream schema validation still rejects incomplete repaired objects.
- OpenAI-compatible providers may differ in how they populate `raw`, `parsed`, and `parsing_error`; the repair logic must tolerate a missing raw `AIMessage` by regenerating from the original invocation and schema.
- The local repair parser verifies that the result is a JSON object but does not independently enforce every JSON Schema constraint; existing schema-specific domain validation must remain in place and must continue to surface invalid or incomplete repaired data.
- Including the failed model output in the repair conversation slightly increases context size, but it should remain an AI-role message and must never be persisted when repair fails.
