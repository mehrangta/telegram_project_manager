# Codex plan for mehrangta/telegram_project_manager#57

Job: `c-0f69e171` · Revision: 1

Preserve the intentional single-message `/brainstorm` flow, but render each complete numbered idea as a separate escaped HTML `<pre>` block so Telegram clients can offer block-level copying. Do not use inline `copy_text` buttons: the repository enforces Telegram’s 256-character limit, while a complete idea can exceed that size. Telegram supports HTML preformatted blocks, while the dedicated copy-button payload remains limited to 256 characters. citeturn0search0turn0search1 No database, schema, command, scheduling, or generation-prompt changes are required.

## Steps

1. **Add opt-in preformatted sections** — Extend `outgoing_message` with an optional `preformatted_prefixes` sequence and pass it into `_render_html`. When a line starts with one of those prefixes, collect that line and the following lines through the next matching prefix or end of text, remove only separator blank lines, HTML-escape the complete section, and wrap it in one `<pre>...</pre>` element. Process these sections before normal heading, field-label, command, or expandable-block rendering. Keep the default empty so every existing response remains byte-for-byte compatible unless it explicitly opts in.
   - Likely files: `src/telegram_project_manager/platform/responses.py`
2. **Mark each idea as copyable** — Keep `_render_result` as the canonical plain-text builder and retain its existing 4096-character completeness check. For successful results, derive prefixes from the actual idea count (`1. ` through `N. `) and pass them through `_deliver` and `_send` to `outgoing_message`. Each preformatted block must contain the complete numbered title, Opportunity, Proposal, Value, and Sources lines for exactly one idea. Repository metadata remains outside the blocks, and failed, cancelled, queued, and completion-notice messages continue using normal formatting.
   - Likely files: `src/telegram_project_manager/bots/ideas/service.py`
3. **Preserve delivery behavior** — Apply the same rendering options to both transport paths: manual brainstorms must edit the existing queued message with HTML parse mode and an explicitly empty keyboard, while scheduled brainstorms must send one new message with the same three blocks. Preserve reply targeting, disabled link previews, temporary completion notifications, error propagation, audit records, workspace cleanup, and the existing rule that an over-budget result fails rather than being truncated.
   - Likely files: `src/telegram_project_manager/bots/ideas/service.py`, `src/telegram_project_manager/platform/telegram_bot.py`
4. **Test generic rendering boundaries** — Add response-helper tests proving that multiple prefixed sections become separate `<pre>` elements; headers and metadata remain outside; `<`, `>`, and `&` inside titles or fields are escaped; the final section works without a trailing blank line; separator whitespace is not copied; and calls without `preformatted_prefixes` preserve current HTML rendering. No Telegram API transport change should be necessary, so existing send/edit payload tests should remain unchanged.
   - Likely files: `tests/test_responses.py`, `tests/test_telegram_bot.py`
5. **Test brainstorm integration** — Update brainstorm rendering and service tests to assert exactly three independent `<pre>` blocks in rank order, each containing one complete idea and its surviving source paths. Assert that no idea is split or truncated, metadata stays outside the blocks, manual edits and scheduled sends both receive the copyable formatting, and failure/cancellation messages do not. Retain near-limit and over-limit coverage to ensure HTML markup does not weaken the plain-text 4096-character guard.
   - Likely files: `tests/test_brainstorm.py`
6. **Document and roll out** — Update user-facing workflow documentation to state that every returned idea is independently copyable while the result remains one Telegram message. This is a presentation-only rollout with no migration or configuration flag: deploy through the normal service update and restart, then smoke-test `/brainstorm` in a private chat and a forum topic, plus one scheduled run. Verify block copying on the Telegram clients the project supports before declaring rollout complete.
   - Likely files: `README.md`, `src/telegram_project_manager/bots/ideas/README.md`

## Risks

- Telegram client versions may differ in how visibly they expose copying for preformatted blocks; verify Android, iOS, and Desktop clients used by the project. If a required client lacks block-level copying, splitting ideas into separate messages would be the fallback, but that would conflict with the repository’s intentional single-message behavior and should require a separate product decision.
- Preformatted blocks trade the current bold Opportunity, Proposal, and Value labels for uniform copyable text inside each idea. Keep repository metadata styled normally so the visual change is scoped to the copyable unit.
- Incorrect section-boundary detection could combine adjacent ideas or omit Sources. Generate exact numbered prefixes from the idea count and cover first, middle, final, sourced, and source-free ideas in tests.
- Dynamic repository or model content containing HTML metacharacters could break Telegram parsing if inserted directly. All preformatted content must pass through `html.escape`; never concatenate raw model text into HTML.
- Telegram’s message limit applies to rendered content, while HTML escaping expands the transmitted payload. Preserve the existing plain-text limit check and test near-limit content with escapable characters against the real Bot API during smoke testing.
- Because the renderer is shared platform code, an opt-in parameter with an empty default is important to prevent formatting changes in code jobs, issue drafts, pull-request lists, and other bot responses.
