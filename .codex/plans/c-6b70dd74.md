# Codex plan for mehrangta/telegram_project_manager#79

Job: `c-6b70dd74` · Revision: 1

The merge-confirmation message currently appears as a standalone Telegram message and remains in the chat after an administrator confirms the merge. This leaves stale confirmation UI in the conversation and disconnects the prompt from the code-job message that initiated it. Scope the change to merge callbacks: send the confirmation as a reply to the message whose Merge button was selected, then delete that confirmation after its Confirm merge button is selected while continuing to dispatch the merge if deletion fails.

## Steps

1. **Thread the merge confirmation** — In the `confirm_merge:<job_id>` callback branch, construct the existing confirmation `OutgoingMessage` with `reply_to_message_id=callback.source_message_id`. Keep the current chat and forum-topic routing, confirmation text, callback data, and keyboard unchanged. The existing Telegram API adapter will emit `reply_parameters` with `allow_sending_without_reply=True`, so a missing or already-deleted source message degrades to an ordinary message instead of preventing confirmation.
   - Likely files: `src/telegram_project_manager/platform/telegram_bot.py`
2. **Delete after merge confirmation** — In the `command:` callback path, distinguish `/merge <job_id>` from `/deploy <job_id>`. After acknowledging the callback as `Action requested`, call the existing best-effort `delete_callback_source` helper for a merge command instead of calling `edit_message_reply_markup`; then synthesize the existing `IncomingMessage` and dispatch `/merge` normally. Retain the current reply-markup removal for deploy confirmations, and do not delete the original code-job message that produced the first Merge button.
   - Likely files: `src/telegram_project_manager/platform/telegram_bot.py`
3. **Preserve adjacent behavior** — Leave direct typed or replied `/merge` commands unchanged because they bypass callback confirmation handling. Preserve job-ID validation, administrator checks, chat/topic scoping, callback acknowledgements, merge-service execution, response formatting, invalid-button behavior, and non-admin silence. Keep `cancel_merge` behavior unchanged: acknowledge cancellation and remove the confirmation keyboard without deleting the message, since the issue requests deletion after confirmation rather than cancellation. No database, schema, configuration, GitHub integration, or merge-service changes are required.
   - Likely files: `src/telegram_project_manager/platform/telegram_bot.py`, `src/telegram_project_manager/bots/pull_request_manager/commands.py`, `src/telegram_project_manager/platform/responses.py`
4. **Update callback tests** — Update `test_merge_button_prompts_then_confirm_dispatches` to assert that the confirmation send includes `reply_to_message_id` equal to the first callback's source message ID, the confirmed merge deletes the confirmation message ID, no merge-related markup edit occurs, and `/merge c-abcdef12` still reaches the router. Keep the deploy test asserting its existing markup-edit behavior so the split cannot accidentally alter deployment confirmation.
   - Likely files: `tests/test_telegram_bot.py`
5. **Cover deletion failure** — Add or extend a callback-polling test with a bot whose `delete_message` raises `TelegramBotApiError`. Assert that confirming merge still acknowledges the callback, dispatches the merge command, sends the router response, and records the existing `Telegram callback source deletion failed` warning. This locks in best-effort cleanup rather than making Telegram deletion a prerequisite for starting the merge.
   - Likely files: `tests/test_telegram_bot.py`
6. **Roll out without migration** — Ship as a normal application update with no feature flag or data migration. After automated validation, perform a Telegram smoke test from a ready code-job message in both a normal chat and, if supported operationally, a forum topic: tap Merge, verify the warning is visibly a reply to that code-job message, tap Confirm merge, verify the warning disappears, and verify the normal merge-queued or failure response still appears.

## Validation

- Run the focused callback suite: `uv run python -m unittest discover -s tests -p 'test_telegram_bot.py'`.
- Run the complete repository suite: `uv run python -m unittest discover -s tests`.
- Manually verify that a merge confirmation replies to the source code-job message and is removed after Confirm merge is selected.
- Manually verify that Cancel leaves the confirmation text with its keyboard removed and that deploy confirmation behavior remains unchanged.
- The current planning environment could not execute the suite without creating a new `.venv`; the repository has `uv` but no base `python` executable or existing virtual environment.

## Risks

- Telegram can reject deletion because the bot lacks permission, the message is too old, or it was already removed; cleanup must remain warning-only so merge dispatch proceeds.
- The original code-job message may disappear before the confirmation is sent; existing `allow_sending_without_reply=True` intentionally permits an unthreaded fallback rather than failing the workflow.
- Combining merge and deploy handling in the current conditional makes an overly broad edit likely to change deployment behavior; split the branches explicitly and retain deploy regression assertions.
- A duplicate merge callback may already be queued before Telegram processes deletion; this change does not introduce new idempotency controls and should continue relying on existing merge job-state validation.
