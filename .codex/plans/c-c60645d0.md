# Codex plan for mehrangta/telegram_project_manager#26

Job: `c-c60645d0` · Revision: 1

Extend the existing 30-second plan-feedback reconciliation loop to inspect each awaiting plan pull request before processing questions or comments. When GitHub reports the PR as non-open, idempotently delete the tracked Telegram plan approval/clarification message, clear `telegram_plan_message_id`, and skip further feedback processing for that job during the poll. Keep the code-job status, branch, workspace, and PR unchanged because the issue requests notification cleanup rather than treating manual closure as `/code discard`. No schema, configuration, command, or deployment migration is required.

## Steps

1. **Expose pull request state** — Add a focused `CodeGitHubService.get_pr_state(repo: str, number: int) -> str` interface that reads `repos/{repo}/pulls/{number}` through the existing `GhRunner` API helper, normalizes the returned `state` to lowercase, and accepts only GitHub's `open` or `closed` values. Raise the existing GitHub/workspace error type for malformed responses so an unknown state is never interpreted as closure.
   - Likely files: `src/telegram_project_manager/bots/code_manager/workspace.py`
2. **Reconcile closure before feedback** — In `CodeJobService.poll_plan_feedback_once`, query PR state for every job returned by `Database.list_plan_feedback_jobs()` before publishing revision questions or listing comments. If the state is `closed`, call `reporter.dismiss_plan_ready(job_id)` and immediately continue to the next job. This covers both `awaiting_clarification` and `awaiting_approval`, prevents closed PR comments from triggering plan edits, and relies on the existing poller started by `recover()` so manually closed PRs are detected after normal startup or restart within the configured 30-second interval.
   - Likely files: `src/telegram_project_manager/bots/code_manager/service.py`, `src/telegram_project_manager/platform/storage/db.py`
3. **Preserve idempotent failure behavior** — Reuse `CodeProgressReporter.dismiss_plan_ready` rather than calling Telegram directly. Successful deletion, including Telegram's existing “message to delete not found” case, clears `telegram_plan_message_id`; an absent message id is a no-op; other Telegram deletion failures leave the id intact so the next poll retries. A GitHub lookup failure must preserve the Telegram message and be logged/retried by the monitor instead of being mistaken for a closed PR. Do not mark the job `discarded`, interrupt Codex, delete the remote branch, clean the workspace, or create a replacement Telegram message.
   - Likely files: `src/telegram_project_manager/bots/code_manager/progress.py`, `src/telegram_project_manager/bots/code_manager/service.py`
4. **Add GitHub interface coverage** — Extend the existing `CodeGitHubService` tests with representative API payloads proving that `open` and `closed` states are normalized correctly and that missing or unsupported state values raise the expected error. Assert the exact pull-request endpoint is requested without introducing additional GitHub CLI calls.
   - Likely files: `tests/test_code_manager.py`
5. **Add closure regression coverage** — Extend `FakeGitHub` with configurable PR state and call tracking. Add an async regression test that creates a planned job, waits for its approval message, changes the fake PR state to `closed`, invokes one feedback poll, and verifies Telegram deletion, clearing of `telegram_plan_message_id`, and no plan-question publication or PR-comment processing after closure. Poll a second time to prove deletion is idempotent. Add a retry case where Telegram deletion initially fails, confirming the stored message id remains and a later poll removes it. Retain the existing authenticated-comment test to prove open PR feedback behavior remains compatible.
   - Likely files: `tests/test_code_manager.py`
6. **Validate and roll out** — Run the focused code-manager tests first, followed by the repository-wide unittest suite. Deployment requires only replacing the application code and restarting the bot; the existing recovery path starts the feedback monitor and automatically reconciles approval messages for already-closed PRs. No database migration or backfill is needed because existing rows already store the PR number and Telegram plan message id.
   - Likely files: `pyproject.toml`, `src/telegram_project_manager/main.py`, `tests/test_code_manager.py`

## Risks

- `list_plan_feedback_jobs()` continues selecting closed jobs whose code-job status remains awaiting clarification or approval, so GitHub state will be rechecked every poll even after the Telegram message is gone. This preserves the issue's narrow scope but may warrant a separate lifecycle-retirement feature if closed jobs accumulate near the current 100-job query limit.
- The current monitor catches failures around the polling pass rather than each individual job; a GitHub failure for one PR may defer later jobs until the next 30-second cycle. The implementation should at minimum preserve messages on lookup failure and may isolate per-job errors if doing so remains a small, testable refactor.
- Treating every non-open state as dismissible includes merged PRs because GitHub represents merged pull requests as closed. That is appropriate for an approval message that can no longer be acted on, but tests should use GitHub's actual `closed` state rather than inventing a separate `merged` state.
- Telegram deletion can fail because of permissions, message age, or transient API errors. Existing reporter behavior intentionally retains the database id for retry; clearing it after an unrecognized failure would silently abandon the stale message.
