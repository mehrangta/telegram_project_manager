# Codex plan for mehrangta/telegram_project_manager#70

Job: `c-27865e8e` · Revision: 1

The bot has no persistent `/goal` lifecycle comparable to Codex, so administrators can only submit finite jobs or scheduled brainstorms. As a result, a chat or forum topic cannot hold one durable objective that keeps progressing and can be viewed, edited, paused, resumed, or cleared. The target contract should mirror current Codex semantics: `/goal set <description>`, `/goal view`, `/goal edit <updated goal>`, `/goal pause`, `/goal resume`, and `/goal clear`, with the goal attached to the active conversation scope. citeturn763684view0turn197976view0 Implement this as a repository-scoped, durable Codex workflow backed by the existing full-access worker and persistent `/do` workspace, with one goal per exact Telegram chat or forum topic. The current baseline is clean: `uv run python -m unittest discover -s tests` passes all 352 tests.

## Risks

- Goals execute Codex with unrestricted host filesystem and network access in a writable repository workspace; broad objectives can cause repeated or unintended changes, so the existing admin allow list, repository validation, prominent warnings, and explicit pause/clear controls are essential.
- A pause, edit, or clear request races with a Codex turn in another process; state transitions and control claims must be transactional, idempotent, and checked again before applying a completed result.
- The shared persistent `/do` workspace can be corrupted by concurrent writers unless `/do` jobs and goal turns use the same repository lane scheduler; separate in-memory schedulers are not sufficient.
- A worker or provider failure may occur after Codex has partially modified files, so interrupted or failed turns must become `blocked` rather than being replayed automatically; `/goal resume` should continue only after the user has reviewed the status.
- Recurring goals can starve explicit work or produce excessive Telegram traffic; `/do` priority, five-minute scheduling gaps, activity-change checks, and message throttling must be covered by deterministic tests.
- Changing or disallowing the active repository after goal creation must not silently redirect the goal; the pinned repository context should remain visible, and failed validation should block the goal until it is cleared or resumed after repair.
- Goal objectives and progress summaries are durable user content and may contain sensitive text; outputs must be redacted consistently, access must remain scoped to the originating chat/topic, and clear should remove goal-specific rows and events.
- Telegram message creation or editing can fail independently of execution; database state and audit events must remain authoritative, and delivery failures must not cause duplicate Codex work.
