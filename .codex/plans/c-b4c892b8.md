# Codex plan for mehrangta/telegram_project_manager#78

Job: `c-b4c892b8` · Revision: 1

The final “Code job ready” Telegram alert is currently sent as a standalone message rather than as a reply to the code job’s tracked progress message. In busy chats and topics, this separates the completion alert from the job context and makes the corresponding request harder to identify. Use the persisted `telegram_message_id` as the reply target only for ready alerts, relying on the existing Telegram send API to fall back to a standalone message when the target is unavailable. This is a localized, backward-compatible change with no database migration or public interface change.

## Steps

1. **Attach ready alerts to tracked jobs** — Update `CodeProgressReporter.notify_terminal(job_id)` to derive a reply target from the loaded job only when `status == "ready"` and `telegram_message_id` is present. Pass that target into `outgoing_message(..., reply_to_message_id=...)`, then forward `outgoing.reply_to_message_id` to `TelegramBotApi.send_message`. Preserve the existing alert text, pull-request link, merge/deploy controls, destination chat, and forum-topic `telegram_thread_id`.
   - Likely files: `src/telegram_project_manager/bots/code_manager/progress.py`
2. **Preserve terminal failure behavior** — Keep failed code-job alerts standalone because the issue specifically requests threading for the “Code job ready” message. Ensure the shared `notify_terminal` path conditionally sets the reply target instead of applying it to both supported terminal statuses, without changing status transitions, audits, cleanup, or error handling in `CodeJobService._report_terminal`.
   - Likely files: `src/telegram_project_manager/bots/code_manager/progress.py`
3. **Use existing persistence and fallback** — Reuse `code_jobs.telegram_message_id`, which `CodeProgressReporter.create` already fills with the Telegram ID returned for the tracked progress message before the job is scheduled. Do not add columns, migrations, or new service parameters. When the value is absent, send the ready alert normally; when the referenced message was deleted or is otherwise unavailable, the existing `TelegramBotApi.send_message` implementation emits `reply_parameters` with `allow_sending_without_reply: true`, allowing Telegram to deliver a standalone alert instead of failing the job notification.
4. **Add focused regression coverage** — Extend the existing successful code-job lifecycle test to assert that the final ready alert’s `reply_to_message_id` equals the job’s persisted `telegram_message_id`, while retaining assertions for chat ID, topic ID, rendered ready text, and merge/deploy controls. Add focused reporter coverage for a ready job without a tracked message ID to verify a standalone send, and assert that a failed terminal alert does not acquire a reply target. Reuse `FakeBot.sent_options` and existing asynchronous wait helpers rather than introducing a new test harness.
   - Likely files: `tests/test_code_manager.py`
5. **Document conversational behavior** — Update the code-job workflow documentation to state that the separate ready notification replies to the tracked code-job message. Keep the terminology aligned with the existing `/issues` documentation, which already calls `telegram_message_id` the code job’s tracked Telegram message.
   - Likely files: `README.md`
6. **Roll out without data migration** — Deploy through the normal application update and restart process; no configuration switch, database backfill, or worker protocol change is required. Existing and in-flight jobs with a stored tracked-message ID gain the reply behavior, while legacy or incomplete rows with a null ID continue receiving standalone ready alerts.

## Validation

- Run `uv run python -m unittest discover -s tests -p 'test_code_manager.py'` to validate ready-alert threading, standalone fallback, unchanged failure behavior, and the surrounding asynchronous code-job lifecycle.
- Run `uv run python -m unittest discover -s tests -p 'test_telegram_bot.py'` to confirm the existing Telegram client still serializes reply targets as `reply_parameters` with `allow_sending_without_reply: true`.
- Run `uv run python -m unittest discover -s tests` for the full repository regression suite.

## Risks

- The repository does not retain the user’s original `/code` command message ID; this plan interprets “actual job” as the bot’s persisted tracked progress message, consistent with the current schema and `/issues` terminology.
- Because `notify_terminal` handles both ready and failed states, an unconditional reply target would silently broaden the issue’s scope; the implementation and tests must condition specifically on `status == "ready"`.
- Recovered or legacy jobs may have a null `telegram_message_id`; the implementation must preserve standalone delivery instead of rejecting or suppressing their ready alerts.
- The tracked message may be deleted before completion; delivery depends on the existing `allow_sending_without_reply` fallback, so no strict-reply mode should be introduced.
- Asynchronous tests can observe status before the terminal send completes; assertions must continue using the repository’s send-count wait helpers before inspecting the final message options.
