# Codex plan for mehrangta/telegram_project_manager#53

Job: `c-620e1953` · Revision: 1

Replace the automatic merge/deploy conflict-recovery strategy with a Codex-assisted merge of the latest base branch into the pull-request branch. The current repository already invokes Codex for textual conflicts encountered during `/code rebase`, but the referenced PR became mergeable only after a `Merge branch 'main' into codex/issue-51-c-10ee1898` commit. Preserve manual `/code rebase`, host-owned Git operations, CI revalidation, bounded retries, and existing durable job states.

## Steps

1. **Separate automatic resolution from manual rebase** — Introduce a clearly named `resolve_conflicts_for_operation(job_id)` entry point for `MergeDeploymentService` and wire it in `main.py`. Keep `/code rebase` mapped to the existing rebase behavior. The automatic entry point must require a ready checked job, an open PR, `deployment_status == resolving_conflicts`, no merge SHA, and no newer active job before queuing work.
   - Likely files: `src/telegram_project_manager/main.py`, `src/telegram_project_manager/bots/pull_request_manager/service.py`, `src/telegram_project_manager/bots/code_manager/service.py`
2. **Add guarded merge workspace operations** — Add workspace primitives that check out and hard-align the local branch to the exact checked remote head, fetch the latest base, and start `git merge --no-commit --no-ff origin/<base>`. Return the fetched base SHA and unmerged paths. Reject sensitive paths, unsupported unresolved states, dirty workspaces, and changed remote heads. After resolution, verify no conflict markers or unmerged entries remain, stage only the original conflict paths, create a host-owned merge commit, and push it as a normal fast-forward guarded against remote-head changes rather than force-pushing.
   - Likely files: `src/telegram_project_manager/bots/code_manager/workspace.py`, `src/telegram_project_manager/integrations/git/local_repository.py`
3. **Create the Codex merge-conflict prompt** — Add a prompt that supplies the untrusted issue context, base branch and SHA, checked PR head, resolution attempt, and exact conflicted paths. Require Codex to inspect both sides, preserve compatible base and issue behavior, modify only listed conflict files, remove markers, run focused validation, and return `CODE_RESULT_SCHEMA`. Continue prohibiting Git, commit, push, GitHub, workflow, secret, and sensitive-file operations inside Codex.
   - Likely files: `src/telegram_project_manager/bots/code_manager/prompts.py`
4. **Implement automatic Codex resolution flow** — When a queued rebase belongs to `deployment_status == resolving_conflicts`, run the merge-based path instead of rewriting commits. Invoke Codex at high effort when the merge reports conflicts, validate its output through the existing structured-result recovery, finish and push the merge commit on the host, then store previous head, base SHA, new head, conflict files, Codex result, validation commands, and attempt number under `result_json.conflict_resolution`. Queue checks for the new SHA and leave the deployment operation pending so successful CI resumes merging.
   - Likely files: `src/telegram_project_manager/bots/code_manager/service.py`, `src/telegram_project_manager/bots/code_manager/prompts.py`, `src/telegram_project_manager/bots/code_manager/workspace.py`
5. **Harden retry and stabilization behavior** — Retain the two-attempt ceiling for a genuinely moving base, but do not perform a second identical operation. After CI, allow GitHub a bounded interval to recalculate mergeability for the newly pushed head. If GitHub still reports conflict and the latest base SHA has advanced, queue another Codex-assisted merge; if the head already contains the same base SHA, fail with an inconsistent GitHub mergeability diagnostic instead of repeating a no-op. Revalidate PR head identity before every merge, commit, push, and final squash merge.
   - Likely files: `src/telegram_project_manager/bots/pull_request_manager/service.py`, `src/telegram_project_manager/bots/pull_request_manager/github.py`, `src/telegram_project_manager/bots/code_manager/service.py`
6. **Preserve durable compatibility and reporting** — Reuse `queued_rebase`, `rebasing`, `resume_phase=rebase`, `deployment_status=resolving_conflicts`, and `deployment_conflict_attempts` so no SQLite migration is required and existing interrupted jobs resume safely after restart. Infer automatic merge resolution from deployment state; ordinary queued rebases remain rebases. Update activity, audit, failure, and Telegram text to say Codex conflict resolution rather than manual automatic rebase, while retaining `/code retry`, `/code rebase`, `/merge`, and `/code status` recovery controls.
   - Likely files: `src/telegram_project_manager/bots/code_manager/service.py`, `src/telegram_project_manager/bots/code_manager/progress.py`, `src/telegram_project_manager/bots/pull_request_manager/service.py`, `src/telegram_project_manager/platform/storage/db.py`, `src/telegram_project_manager/platform/responses.py`
7. **Document and regression-test the workflow** — Document that merge/deploy conflict recovery merges the latest base into the PR branch, lets Codex resolve guarded content conflicts, pushes a merge commit, reruns CI, and resumes the requested operation; `/code rebase` remains explicit history rewriting. Add service and workspace tests for clean merges, Codex-resolved conflicts, exact-head checkout, sensitive or non-conflict edits, push races, moving bases, stale GitHub mergeability, restart recovery, CI failure, retry exhaustion, and unchanged manual rebase behavior.
   - Likely files: `README.md`, `src/telegram_project_manager/bots/pull_request_manager/README.md`, `tests/test_code_manager.py`, `tests/test_pull_request_manager.py`, `tests/test_local_repository.py`, `tests/test_responses.py`, `tests/test_commands.py`

## Validation

- Run focused conflict and orchestration tests: `uv run python -m unittest -v tests.test_code_manager tests.test_pull_request_manager tests.test_local_repository tests.test_responses tests.test_commands`.
- Run the complete repository suite: `uv run python -m unittest discover -s tests -v`.
- Verify a simulated conflicting PR produces one host-created merge commit whose first parent is the checked PR head and second parent is the fetched base SHA, then queues CI for that exact new head.
- Verify restart recovery converts an interrupted automatic operation back to the durable queue and resumes merge-based conflict resolution without resetting the deployment attempt count.
- Verify manual `/code rebase` still rebases and uses force-with-lease, while automatic merge/deploy recovery uses a normal fast-forward push.
- Verify Codex failures, invalid structured output, sensitive paths, binary or unresolved conflicts, unexpected file edits, remote-head races, failed CI, and exhausted retries leave the PR open and expose existing retry/status controls.

## Risks

- Adding a merge commit changes the PR branch history shape, although the final protected-branch operation remains the existing squash merge and the issue branch is not force-rewritten.
- A repository may prohibit merge commits on feature branches or reject bot pushes; surface the Git error and leave the PR open rather than bypassing protection.
- Codex can produce an incorrect semantic resolution even when markers are removed; path restrictions, host validation, CI, exact-head checks, and normal review remain mandatory.
- Binary, rename/delete, submodule, workflow, secret, or sensitive-path conflicts may not be safely editable by Codex and must fail closed with actionable diagnostics.
- The base branch can advance during resolution or CI; compare captured base and head SHAs before deciding whether another bounded attempt is meaningful.
- GitHub mergeability can remain temporarily stale after a push; bounded stabilization polling is required to avoid consuming retries on the same head and base.
- Existing interrupted automatic rebase jobs will resume under merge-based semantics after rollout; this is safe because recovery recreates the workspace from the checked remote head, but it should be covered explicitly by tests.
