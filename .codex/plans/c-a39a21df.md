# Codex plan for mehrangta/telegram_project_manager#65

Job: `c-a39a21df` · Revision: 1

Update Telegram callback handling so the existing “Issue created.” message is deleted when either its Plan or Code button is clicked, while preserving the current command payloads, code-job behavior, issue link behavior before selection, and best-effort failure handling. No database, schema, configuration, or public command changes are required.

## Steps

1. **Classify issue-created code actions** — In the Telegram callback module, add a narrowly scoped matcher for the four callback command forms currently generated by IssueManager: `/code owner/repo#N`, `/code #N`, `/code --skip-plan owner/repo#N`, and `/code --skip-plan #N`. Keep this classification separate from general `/code` controls so callbacks such as `/code rebase c-...`, retry, approval, edit, discard, and status do not delete their source notifications. Do not import CodeManager parsing constants into the platform layer, which would invert the current dependency direction.
   - Likely files: `src/telegram_project_manager/platform/telegram_bot.py`
2. **Delete the source before dispatch** — In `run_polling` callback dispatch, after validating the generic `command:` payload and acknowledging the callback as “Action requested,” invoke the existing `delete_callback_source` helper when the command matches either the existing issue-draft Confirm/Cancel matcher or the new issue-created Plan/Code matcher. Then construct the existing IncomingMessage and dispatch the `/code` command unchanged. This preserves the current data flow: IssueManager creates the GitHub issue and renders buttons; Telegram polling converts the selected callback back into a command; CodeManager resolves the issue reference and queues either planning or skip-plan execution.
   - Likely files: `src/telegram_project_manager/platform/telegram_bot.py`
3. **Preserve failure and compatibility behavior** — Keep deletion best-effort: TelegramBotApiError from `deleteMessage` must log the existing warning and must not prevent the Plan or Code command from being dispatched. Leave callback acknowledgement failure behavior unchanged. Do not alter `_code_callback`, button labels, callback payloads, CodeManager parsing, or issue-created message formatting, so already-sent cards remain actionable after rollout and long repository names continue using the existing short `#N` fallback. No storage migration or state transition is needed.
   - Likely files: `src/telegram_project_manager/platform/telegram_bot.py`, `src/telegram_project_manager/bots/issue_manager/commands.py`, `src/telegram_project_manager/bots/code_manager/commands.py`
4. **Add callback regression coverage** — Extend Telegram callback polling tests with Plan and Code button updates and assert that each exact command is dispatched, its source message ID is deleted, and the callback is acknowledged. Cover both repository-qualified and short fallback issue references, including `--skip-plan`. Retain or strengthen the existing `/code rebase c-...` assertion that unrelated code-job action cards are not deleted. Extend the deletion-failure case with an issue-created Plan or Code callback and assert that dispatch still occurs and the warning is logged. Existing IssueManager tests should continue verifying that the button payload formats remain unchanged.
   - Likely files: `tests/test_telegram_bot.py`, `tests/test_issue_manager.py`
5. **Validate and roll out** — Run the focused callback suite with `uv run python -m unittest discover -s tests -p 'test_telegram_bot.py' -v`, then run the complete suite with `uv run python -m unittest discover -s tests -v`. The focused suite also runs in a dependency-light environment as `PYTHONPATH=src python3 -m unittest discover -s tests -p 'test_telegram_bot.py' -v`; it currently passes 26 tests. Deploy through the normal bot process restart with no database migration. Manually confirm in a Telegram test chat or topic that Plan removes the card and starts planning, Code removes it and starts skip-plan execution, the Issue URL works before either selection, and deletion rejection does not block the selected action.
   - Likely files: `tests/test_telegram_bot.py`, `tests/test_issue_manager.py`, `pyproject.toml`

## Validation

- Plan callback with `command:/code owner/repo#12` deletes its source message and dispatches `/code owner/repo#12`.
- Code callback with `command:/code --skip-plan owner/repo#12` deletes its source message and dispatches the unchanged command.
- Short fallback callbacks `/code #12` and `/code --skip-plan #12` receive the same deletion behavior.
- Unrelated callbacks such as `/code rebase c-abcdef12` continue dispatching without deleting their source message.
- A Telegram `deleteMessage` failure logs a warning but still acknowledges and dispatches the selected Plan or Code action.
- Existing issue-created keyboard tests continue passing without callback payload or label changes.
- Run focused validation: `uv run python -m unittest discover -s tests -p 'test_telegram_bot.py' -v`.
- Run full validation: `uv run python -m unittest discover -s tests -v`.

## Risks

- Telegram may reject deletion because the bot lacks deletion rights or the message is no longer deletable; the existing best-effort helper limits this to a warning and preserves action dispatch.
- Matching all `/code` callbacks would remove unrelated code-job notifications, so the matcher must require an issue reference and only the optional `--skip-plan` flag.
- Deletion occurs before CodeManager completes startup, consistent with existing issue-draft action handling and the issue’s click-based requirement; if job startup later fails, the card remains deleted but the normal error response is still sent.
- Rapid duplicate callback delivery could still request the same action more than once; deleting the card reduces repeat interaction but does not add new job-level idempotency.
- If future features reuse the same `/code [--skip-plan] <issue-reference>` callback shape on messages that should remain visible, the callback contract will need an explicit action prefix or source metadata rather than broadening this matcher.
