# Codex plan for mehrangta/telegram_project_manager#41

Job: `c-1a7b6674` · Revision: 1

Implement `/prs` as the pull-request equivalent of `/issues`: for the active repository in the current Telegram chat or topic, publish up to 20 open pull requests ordered by most recently updated and refresh that message every 60 seconds. Store PR-list messages separately so `/prs` and `/issues` coexist independently. The issue is decision-complete; no material product preference remains unresolved.

## Steps

1. **Add pull-request reader** — Create a repository-level GitHub reader with a `PullRequestSummary` value object containing `number`, normalized `title`, and `url`, plus `GhPullRequestReader.list_open_pull_requests(repo, limit=20)`. Run `gh pr list --repo <repo> --state open --limit <limit> --search sort:updated-desc --json number,title`; preserve CLI ordering, defensively slice to the requested limit, normalize whitespace, truncate titles using the existing 120-character issue-title convention, and construct the canonical encoded `https://github.com/<owner>/<repo>/pull/<number>` URL. Reject non-positive limits, invalid JSON, non-list responses, malformed entries, invalid numbers, non-string or empty titles, while propagating `GhError` unchanged for command-level reporting.
   - Likely files: `src/telegram_project_manager/integrations/gh/pull_requests.py`, `tests/test_github_pull_requests.py`
2. **Add independent list persistence** — Create an idempotent `pull_request_list_messages` table alongside `issue_list_messages`, using the same columns and a primary key on normalized `(telegram_chat_id, telegram_thread_id)`. Add `get_pull_request_list_message`, `list_pull_request_list_messages`, `upsert_pull_request_list_message`, `update_pull_request_list_render_hash`, and `delete_pull_request_list_message` methods with the same `None` thread-to-zero encoding and conditional update/delete safeguards used by issue lists. Do not migrate, rename, or repurpose `issue_list_messages`; this preserves existing tracked issue messages and permits one current issue list plus one current PR list in every chat/topic.
   - Likely files: `src/telegram_project_manager/platform/storage/db.py`, `tests/test_commands.py`, `tests/test_pull_request_list.py`
3. **Implement refreshing PR lists** — Add `PullRequestListService` and `PullRequestListError`, following the tested `IssueListService` lifecycle without changing `/issues`. `publish` fetches through `asyncio.to_thread`, renders an escaped HTML message, sends it with link previews disabled, records the Telegram message ID and render hash, and deletes the newly sent message if persistence fails. Render `No open pull requests for <repo>.` for an empty result; otherwise render `Open pull requests for <repo>:` followed by linked `#<number> — <title>` rows. Keep the list view-only: do not emit `/code`, `/merge`, or `/deploy` commands because `/code` rejects pull requests and merge/deploy require internal code-job IDs. Use per-chat/topic locks, render hashes, and stale-target checks so repeated `/prs` calls supersede only the priorPR
   - Likely files: `src/telegram_project_manager/bots/pull_request_manager/pull_request_list.py`, `tests/test_pull_request_list.py`
4. **Add refresh recovery handling** — Give `PullRequestListService` one recoverable 60-second background task. During each refresh, remove records for repositories no longer allowed, group remaining targets by repository so each repository is queried once per cycle, skip unchanged render hashes, and edit only records still matching the captured message ID and repository. Treat Telegram's `message is not modified` response as successful hash synchronization; remove records for permanent missing/uneditable/chat-access errors; retain records after transient GitHub, database, or Telegram failures; sanitize error text; and audit failures as `prs.refresh` with repository and optional chat/topic context. Make `recover` idempotent and make `shutdown` cancel and await the task.
   - Likely files: `src/telegram_project_manager/bots/pull_request_manager/pull_request_list.py`, `tests/test_pull_request_list.py`
5. **Route the `/prs` command** — Extend `PullRequestManager` with a required `PullRequestListService` dependency and recognize `/prs`, including Telegram's `/prs@BotName` form, before the existing `/merge` and `/deploy` branches. Apply the manager's existing admin check, reject arguments with `Usage: /prs`, resolve settings through `Database.get_scope_settings(chat_id, thread_id)`, require an active allowed repository, and pass the exact chat/topic IDs to `publish`. Successful publication returns `None` because the service already sends the response. Convert `PullRequestListError` into `Pull requests not loaded.\nReason: <safe error>` and audit `prs.list` as failed with the repository and error. Leave merge/deploy parsing, ownership checks, and service calls unchanged.
   - Likely files: `src/telegram_project_manager/bots/pull_request_manager/commands.py`, `tests/test_pull_request_manager.py`
6. **Wire process lifecycle** — In bot startup, construct `GhPullRequestReader` from the shared `GhRunner`, construct `PullRequestListService` from the existing database and Telegram API, and inject it into `PullRequestManager`. Start its recovery task alongside `IssueListService.recover`, and always call its shutdown method from the existing `finally` block. Keep repository-wide listing separate from `DeploymentGitHubService`, which operates on a known code-job PR URL and has different validation requirements.
   - Likely files: `src/telegram_project_manager/main.py`
7. **Update command documentation** — Add `/prs` next to `/issues` in the Telegram `/help` output and README common-command table, describing it only as listing open pull requests for the active repository. Avoid documenting filters, pagination, closed PRs, or direct merge actions because the issue does not request those behaviors.
   - Likely files: `src/telegram_project_manager/bots/commit_manager/commands.py`, `README.md`, `tests/test_commands.py`
8. **Validate compatibility and rollout** — Extend the legacy-database initialization test to assert that `pull_request_list_messages` is created while existing chat settings and `issue_list_messages` remain intact. Test that `/issues` and `/prs` can both be published in the same chat/topic without replacing each other's storage records. Deployment requires only the normal application restart: `Database.initialize` creates the new table idempotently, existing issue trackers continue refreshing, and the newly started PR scheduler begins managing only messages created through `/prs`.
   - Likely files: `src/telegram_project_manager/platform/storage/db.py`, `tests/test_commands.py`, `tests/test_issue_list.py`, `tests/test_pull_request_list.py`

- Manually select an allowed repository, invoke `/issues` and `/prs` in the same chat and in separate forum topics, then verify each command retains and refreshes its own latest message.
- Manually verify open draft and non-draft pull requests appear, closed and merged pull requests do not, links target the correct GitHub PR pages, empty repositories show the empty-state text, and GitHub authentication failures return the sanitized command error without creating a tracker.

## Risks

- The existing `issue_list_messages` primary key permits only one record per chat/topic, so reusing that table would cause `/prs` and `/issues` to overwrite each other; independent PR-list persistence is required.
- Running a second 60-second refresher increases GitHub CLI traffic. Grouping targets by repository limits the PR service to one `gh pr list` call per tracked repository per cycle, but installations tracking many repositories may see additional latency or rate-limit pressure.
- Copying issue-list lifecycle behavior into a parallel service can drift over time. The implementation should preserve the same locking, stale-record, hash, Telegram-error, audit, recovery, and shutdown semantics and cover them with equivalent tests.
- Telegram messages have size limits, and HTML escaping can expand adversarial titles. The established 20-item and 120-character title limits reduce this risk, but rendering tests should include escaped characters and long titles.
- Arbitrary listed PRs may not correspond to managed code jobs. Adding merge/deploy buttons or commands based only on PR numbers would bypass current chat/topic, checked-head, and deployment-state protections, so `/prs` must remain view-only.
- If the new scheduler is started but omitted from shutdown, tests and service termination can leave a pending task; startup and `finally` cleanup must be updated together.
