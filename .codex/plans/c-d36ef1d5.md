# Codex plan for mehrangta/telegram_project_manager#83

Job: `c-d36ef1d5` · Revision: 1

The code-job flow loses the Telegram message that originally initiated the work as it moves from `/issue` drafting through confirmation, callback dispatch, and asynchronous job creation. Consequently, the tracked Codex status card is sent as a standalone message, making it harder to connect the job to the user's request in busy chats and topics. The implementation should persist a dedicated reply target across issue drafts and code jobs, propagate it through button callbacks, and use it when creating the tracked code-job message while retaining Telegram's standalone fallback behavior.

## Steps

1. **Persist explicit Telegram reply targets** — Add nullable `telegram_reply_to_message_id` columns to both `issue_drafts` and `code_jobs`. Include the columns in fresh-table definitions and add them through `Database._ensure_column` for existing SQLite databases. Update `create_issue_draft` and `create_code_job` inserts to accept the optional values without changing the meaning of `code_jobs.telegram_message_id`, which must remain the ID of the bot's editable tracked status card. Add `telegram_reply_to_message_id` to the allowed code-job update columns only if later mutation is required; otherwise keep it immutable after creation.
   - Likely files: `src/telegram_project_manager/platform/storage/db.py`, `tests/test_commands.py`
2. **Capture the original issue request** — Extend `IssuePlanner.create_draft` with an optional `telegram_reply_to_message_id` keyword argument and persist it in the issue draft. Pass the incoming `/issue` message ID from `IssueManager.create`; album requests should use the existing normalized base message ID. During `IssueManager.confirm`, retrieve the persisted draft target and set it on the returned `Issue created` `OutgoingMessage`. This makes the issue action card a reply to the original `/issue` even when confirmation occurs through a later typed command, a preview button, or after draft revisions. Preserve existing validation, issue creation idempotency, callback contents, topic destination, and failure responses; drafts created before deployment or outside Telegram retain a null target and produce standalone cards.
   - Likely files: `src/telegram_project_manager/bots/issue_manager/planner.py`, `src/telegram_project_manager/bots/issue_manager/commands.py`, `tests/test_issue_manager.py`, `tests/test_repository_context.py`
3. **Propagate origin through callbacks** — Add an optional reply-target field such as `reply_target_message_id` to `IncomingMessage` and preserve it when `TelegramRouter` rebuilds cleaned messages. Normal Telegram messages should identify their own `message_id` as the target. For callback queries, inspect the button source message before it is deleted: if it is a reply, use `source.reply_to_message.message_id`; otherwise fall back to the callback source message ID. Copy this field into the synthetic `IncomingMessage` created for `command:` callbacks. This allows Plan and Code buttons on the replied issue card to carry the original `/issue` ID through dispatch, while callbacks from unrelated bot messages keep their existing source-message context. Missing or malformed reply metadata must remain non-fatal.
   - Likely files: `src/telegram_project_manager/platform/router.py`, `src/telegram_project_manager/platform/telegram_bot.py`, `tests/test_telegram_bot.py`
4. **Attach the tracked code job** — Update `CodeManager._start` to pass the resolved reply target into `CodeJobService.create_job`, using the propagated callback target when present and the incoming command's own `message_id` for direct `/code` requests. Add an optional `reply_to_message_id` keyword parameter to `CodeJobService.create_job`, defaulting to `None` for compatibility with internal callers and tests, and store it as `code_jobs.telegram_reply_to_message_id`. Update `CodeProgressReporter.create` to forward that persisted value to `TelegramBotApi.send_message`. Continue storing the returned bot message ID in `code_jobs.telegram_message_id` so edits, `/issues` links, and the existing ready-notification reply chain remain unchanged. Do not broaden the change to plan-ready, failure, merge, or deployment notifications; a
   - Likely files: `src/telegram_project_manager/bots/code_manager/commands.py`, `src/telegram_project_manager/bots/code_manager/service.py`, `src/telegram_project_manager/bots/code_manager/progress.py`
5. **Cover end-to-end reply behavior** — Add focused tests proving that a direct `/code` request uses its own message ID, an issue-card Code or Plan callback carries the original replied-to `/issue` ID despite deletion of the issue card, and the code-job row persists that value. Assert that `CodeProgressReporter.create` sends the tracked card with the persisted reply target while retaining the chat and forum-topic IDs and saving the returned status-card ID separately. Add null-target coverage for legacy or programmatic jobs and verify the send remains standalone. Extend issue tests to verify the original message ID reaches the draft and that the created issue card replies to it. Extend the database upgrade test to verify both new columns are added without losing existing data.

Roll out through the normal application update and restart process; `Database.initialize` performs the additive nullable migration, so no configuration flag, backfill, worker protocol change, or downtime migration is required. Existing drafts and jobs with null targets continue using standalone delivery, and Telegram's existing `allow_sending_without_reply: true` behavior delivers messages even when a stored target was deleted or is no longer replyable.

## Risks

- `code_jobs.telegram_message_id` already means the bot's tracked status-card ID; overloading it with the user request ID would break message edits, `/issues` links, and ready-alert threading, so the new reply target must remain a separate field.
- Telegram may omit `reply_to_message` from a callback source in edge cases; callback parsing must tolerate that and fall back to the source message or standalone delivery rather than preventing job creation.
- Issue action cards are deleted before the synthetic `/code` command completes, so the callback reply target must be extracted before deletion; otherwise the reporter may attempt to reply to the deleted card and Telegram will fall back to a standalone message.
- The original user message may have been deleted or become unavailable before the job starts; the existing `allow_sending_without_reply: true` setting must remain enabled so notification delivery does not fail.
- Legacy issue drafts, legacy code jobs, and non-Telegram service callers have no reply target. Nullable columns and optional service parameters must preserve their current standalone behavior without requiring a backfill.
- Expanding reply behavior to plan-ready, failed, merge, or deployment notifications would change unrelated conversational behavior. The implementation should limit this issue to the tracked code-job card and rely on the existing ready notification replying to that tracked card.
