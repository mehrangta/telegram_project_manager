# Codex plan for mehrangta/telegram_project_manager#94

Job: `c-98c85b50` · Revision: 1

The “Issue created” Telegram confirmation is a static response whose message ID is not persisted, so it cannot reflect later GitHub state changes. When the issue is closed outside Telegram, its Plan, Code, Plan & Code, and Close buttons remain visible even though code-job creation will subsequently reject the closed issue. Implement a durable, periodically refreshed confirmation service that preserves the issue link but removes all action callbacks after closure.

## Steps

1. **Persist live confirmation identity** — Extend `issue_drafts` with a nullable `telegram_confirmation_message_id` column in both the fresh schema and the repository’s `_ensure_column` migration path. Add database methods to set the message only while the draft is in `created` state, list tracked created issues with valid GitHub identifiers, conditionally clear a message by draft/message ID, and clear a matching tracker after a callback source is successfully deleted. Conditional updates must prevent stale refresh snapshots from clearing or editing a newer replacement message.
   - Likely files: `src/telegram_project_manager/platform/storage/db.py`
2. **Expose validated GitHub issue state** — Add `GhIssueReader.get_issue_state(repo, number)` using the existing structured `gh api` integration for `repos/{repo}/issues/{number}`. Normalize case, accept only `open` or `closed`, reject pull-request payloads and malformed or missing states, and propagate `GhError` so the refresh layer can distinguish an unavailable check from a confirmed closure.
   - Likely files: `src/telegram_project_manager/integrations/gh/issues.py`, `tests/test_github_issues.py`
3. **Implement live confirmation service** — Add an `IssueConfirmationService` owned by the issue-manager package. It should render the current created confirmation with the existing Plan, Code, Plan & Code, Issue, and Close callbacks; send it as a reply to the original `/issue` message; capture and persist Telegram’s returned message ID; reuse or replace an already tracked confirmation instead of producing duplicates; and run a restart-safe 60-second refresh task using per-draft locks. For each tracked issue, leave an open issue unchanged; when GitHub reports `closed`, edit the same Telegram message to an `Issue closed.` representation containing issue details and only the URL-based Issue button, then mark the draft closed and clear its tracking pointer. A transient GitHub or Telegram failure must be audited and retained for retry,;
   - Likely files: `src/telegram_project_manager/bots/issue_manager/progress.py`
4. **Handle terminal message failures safely** — Treat Telegram “message is not modified” as success. Treat permanent edit failures such as missing, uneditable, blocked-chat, or permission errors as terminal: clear the tracker and persist the confirmed GitHub closed state because no stale message remains editable. For transient edit failures, keep both `status='created'` and the message pointer so the next cycle retries. If initial send or persistence fails after GitHub has created the issue, audit the failure, delete any untracked sent message when possible, and return a non-live fallback confirmation with issue details and the Issue URL only—never static Plan or Code actions that cannot later be retired.
   - Likely files: `src/telegram_project_manager/bots/issue_manager/progress.py`, `src/telegram_project_manager/platform/storage/db.py`
5. **Route issue commands through tracker** — Inject `IssueConfirmationService` into `IssueManager`. Make the `/confirm` path asynchronous: execute the existing idempotent GitHub creation, then let the service send and register the live confirmation, returning `None` when it owns delivery. Keep callback payload formats and the 64-byte long-repository fallback unchanged. After `/close` succeeds, ask the service to retire any still-present tracked confirmation immediately; this covers typed closes and callback-source deletion failures while preserving the existing human-readable close response.
   - Likely files: `src/telegram_project_manager/bots/issue_manager/commands.py`, `src/telegram_project_manager/bots/issue_manager/executor.py`
6. **Wire lifecycle and callback cleanup** — Construct one shared `GhIssueReader`, use it for both `/issues` and live confirmations, inject the confirmation service into `IssueManager`, start it during `run_bot` recovery, and shut it down in `finally`. Update callback-source deletion to report success and, only after a successful deletion of an issue confirm/cancel/close or issue code-action message, conditionally clear a matching confirmation tracker through the router database. Database cleanup failures must be logged or audited without blocking command dispatch; Telegram deletion failures must leave tracking intact so a later close can still remove the actions.
   - Likely files: `src/telegram_project_manager/main.py`, `src/telegram_project_manager/platform/telegram_bot.py`, `src/telegram_project_manager/platform/router.py`
7. **Cover lifecycle and compatibility** — Add focused asynchronous service tests for initial publish and reply targeting, persisted recovery, duplicate confirmation reuse, open-state no-op, externally closed rendering, removal of all callback buttons while retaining the Issue URL, transient GitHub failure, retryable Telegram failure, permanent missing-message cleanup, stale-snapshot protection, and scheduler shutdown. Update issue-manager tests for asynchronous confirmation delivery, fallback behavior, immediate local-close retirement, long callback-data compatibility, and idempotent creation. Extend Telegram callback tests to verify successful deletion clears a matching tracker while deletion failure preserves it and still dispatches the command. Correct the directly related stale assertion that currently supplies six issue code/
   - Likely files: `tests/test_issue_confirmation.py`, `tests/test_issue_manager.py`, `tests/test_github_issues.py`, `tests/test_telegram_bot.py`
8. **Roll out without historical backfill** — Rely on the additive SQLite migration during normal startup; no destructive migration or configuration flag is needed. Only confirmations sent after deployment become live because existing Telegram message IDs cannot be reconstructed safely. External GitHub closure should remove actions within one refresh interval, while the existing `CodeGitHubService.get_issue` open-state validation remains the final race-safe guard if a button is pressed before the next poll.
   - Likely files: `src/telegram_project_manager/platform/storage/db.py`, `src/telegram_project_manager/main.py`, `src/telegram_project_manager/bots/code_manager/workspace.py`

## Risks

- Polling performs one GitHub state lookup per tracked open confirmation every 60 seconds; successful action-message deletion, confirmed closure, and permanent Telegram failures must prune trackers to prevent indefinite API load.
- GitHub can close an issue immediately before a Telegram callback is pressed. The UI update is eventually consistent, so the existing server-side open-state check in `CodeGitHubService.get_issue` must remain unchanged as the authoritative safety gate.
- A transient Telegram edit failure temporarily leaves stale controls visible. Retaining the tracker for retry and relying on the GitHub open-state validation avoids unsafe execution without incorrectly declaring the message updated.
- Local `/close` currently deletes callback-source messages before dispatch. Cleanup must remain conditional and the close command must independently retire a surviving tracked message so deletion failures cannot leave permanent actions.
- Existing confirmation messages cannot be adopted because their Telegram message IDs were never stored; attempting heuristic backfill could target unrelated messages, so rollout intentionally affects only newly published confirmations.
- The issue draft `status` field represents both local workflow and terminal GitHub closure. The implementation should only transition `created` to `closed` after GitHub explicitly reports closure or the local close operation succeeds; malformed responses and permission failures must not be interpreted as closure.
