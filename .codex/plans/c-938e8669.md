# Codex plan for mehrangta/telegram_project_manager#82

Job: `c-938e8669` · Revision: 1

Deployment actions currently leave the retained Telegram deployment confirmation as a static message while phase changes are written only to the separate code-job progress card. Users therefore see multiple deployment-related messages and cannot use the deployment message itself to tell whether the bot is merging, resolving conflicts, dispatching, running, finished, or failed. Convert the retained confirmation, or a newly created reply for typed commands, into one persisted live deployment-status message that follows the existing deployment state machine through its terminal outcome. Keep the original code-job card and merge-only behavior unchanged for compatibility.

## Steps

1. **Persist the deployment message identity** — Add a nullable `telegram_deployment_message_id` column to `code_jobs`, include it in fresh-table creation and the idempotent `_ensure_column` upgrade path, and allow it through `update_code_job`. Continue decoding rows generically so existing databases receive the column without data migration and existing jobs default to no tracked deployment message.
   - Likely files: `src/telegram_project_manager/platform/storage/db.py`
2. **Preserve callback message context** — Extend `IncomingMessage` with a nullable `callback_source_message_id`. Populate it only when dispatching callback commands, preserve it when `TelegramRouter` rebuilds cleaned messages, and leave ordinary Telegram messages with this field unset so user-authored command messages are never treated as bot-editable messages. Retain the current removal of deployment confirmation buttons before dispatch.
   - Likely files: `src/telegram_project_manager/platform/router.py`, `src/telegram_project_manager/platform/telegram_bot.py`
3. **Attach deployment starts to one message** — Extend `MergeDeploymentService.start_deploy` with optional `status_message_id` and `reply_to_message_id` keyword arguments while leaving `start`, `start_merge`, and context-free callers backward compatible. `PullRequestManager` should pass the callback confirmation ID as `status_message_id`; for a typed `/deploy`, pass the user command ID as `reply_to_message_id` so the reporter sends a bot-owned status reply. After the atomic `start_code_job_operation` succeeds, set `latest_activity` to the queued deployment activity, establish the live message before scheduling background work, and return `None` when that message was successfully established so polling does not send the old static acknowledgement. If Telegram setup fails, log and audit the presentation failure, continue the deployment,하고
   - Likely files: `src/telegram_project_manager/bots/pull_request_manager/commands.py`, `src/telegram_project_manager/bots/pull_request_manager/service.py`
4. **Render and refresh live deployment status** — Add deployment-specific reporter methods that either edit the retained confirmation or send and persist a new status message. Render only existing state: a phase-aware heading, code-job ID, repository, humanized `deployment_status`, `latest_activity`, elapsed deployment time, merge SHA when available, workflow-run URL when discovered, terminal error when present, and `/code status` access. Reuse `outgoing_message` for escaping, expandable errors, native links, and empty keyboard removal. Every existing deployment transition already calls `reporter.refresh`; extend that path to refresh the code-job card and the deployment message independently under locks and rate limiting so failure to edit either message never blocks GitHub work or the other message.
   - Likely files: `src/telegram_project_manager/bots/code_manager/progress.py`, `src/telegram_project_manager/bots/pull_request_manager/service.py`
5. **Consolidate terminal notifications and recovery** — Change `notify_deployment` to finalize the persisted deployment message instead of sending a duplicate success or failure notification. Preserve the existing standalone terminal notification as a fallback for legacy jobs or unrecoverable missing-message cases. During `recover`, ensure active deploy-mode jobs without a stored deployment message receive one before monitoring resumes; jobs with an ID should continue editing the same message. Treat Telegram's `message is not modified` response as success, recreate and persist a replacement only for definitive missing or no-longer-editable message errors, and merely log transient API failures. Do not alter deployment statuses, GitHub dispatch semantics, retry behavior, merge-only notifications, or automatic conflict resolution.
   - Likely files: `src/telegram_project_manager/bots/code_manager/progress.py`, `src/telegram_project_manager/bots/pull_request_manager/service.py`
6. **Document and validate the lifecycle** — Update the deployment workflow documentation to state that confirmation becomes a live status message and reaches the final result in place. Add focused tests for schema upgrade and persistence, callback ID propagation, typed-command reply creation, confirmation editing, phase rendering, success and failure finalization without duplicate sends, Telegram edit failure isolation, deployment retry reuse, active-job recovery, and unchanged merge behavior. Run the focused unittest modules first, then the complete repository suite.
   - Likely files: `README.md`, `tests/test_pull_request_manager.py`, `tests/test_telegram_bot.py`, `tests/test_code_manager.py`

- Manual Telegram check: run `/deploy c-12345678` directly and verify one bot reply is created, updated in place, retains the deployment-run link when available, and does not edit the user-authored command message.
- Restart check: stop and restart the bot while a deployment is active and verify recovery resumes the stored message, or creates one for a pre-upgrade active row, without redispatching an already dispatched workflow.

## Risks

- Telegram message creation and SQLite persistence cannot be atomic; a process crash after sending but before storing the message ID can leave one orphaned status message. Keep creation serialized per job and make subsequent recovery prefer the persisted canonical ID.
- Some old confirmation messages may have been deleted or may no longer be editable. Replacement should occur only for definitive Telegram errors to avoid producing duplicate messages during transient API failures.
- Refreshing both the code-job card and deployment message increases Telegram edit volume. Preserve the reporter's existing minimum interval, skip unchanged rendered output, and isolate failures between the two edits.
- Existing active deployments have no `telegram_deployment_message_id`. The nullable migration and recovery fallback must support these rows without changing their deployment state or dispatching their workflow twice.
- Changing `start_deploy` to optionally return `None` affects command-handler expectations. Keep context-free service calls returning the existing text response and update fakes and type annotations explicitly.
