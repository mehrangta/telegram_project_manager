Remove the current defect-oriented framing from the Codex prompt, transient response schema, parser, Telegram output, tests, and documentation. Keep commands, scheduling, repository resolution, queue behavior, persistence, and failure handling unchanged; no database migration or rollout flag is required.

## Steps

1. **Define the new brainstorming contract** — Update `BRAINSTORM_DEVELOPER_INSTRUCTIONS` and `BRAINSTORM_PROMPT` to ask for exactly three distinct ideas for new capabilities, workflows, integrations, or meaningful extensions supported by repository evidence. Rank ideas by expected value, repository fit, feasibility, and confidence. Explicitly reject bug reports, vulnerability findings, correctness fixes, maintenance, dependency updates, test coverage, documentation cleanup, performance tuning, and refactors as standalone ideas; allow supporting technical work only when it is an implementation component of a proposed new capability. Continue requiring repository inspection, repository-relative evidence paths, no network or file modifications, no already-implemented ideas, and JSON-only output.

2. **Replace defect-oriented response vocabulary** — Change the transient structured-output contract from `improvements` containing `problem`, `recommendation`, and `benefit` to `ideas` containing `title`, `opportunity`, `proposal`, `value`, and `sources`. Rename the item dataclass from `Improvement` to `BrainstormIdea`, expose `BrainstormResponse.ideas`, and update constants and validation errors to use idea terminology. Preserve the existing limits, exactly-three constraint, case-insensitive title uniqueness, required non-empty detail fields, source normalization, deduplication, truncation, and maximum source count. This payload is exchanged only between the Codex turn and the running service and is not persisted, so backward parsing of the old shape is unnecessary.
   - Likely files: `src/telegram_project_manager/bots/ideas/schemas.py`

## Risks

- LLM focus is probabilistic: an idea may disguise a bug fix as a feature. Explicit exclusions, opportunity-oriented schema fields, prompt-contract tests, and manual output review reduce but cannot eliminate this risk.
- A strict exclusion of maintenance work could hide infrastructure changes that enable valuable functionality. The prompt should permit such work only as a clearly subordinate part of a net-new capability proposal.
- Renaming the transient JSON shape requires the prompt, schema, parser, fake Codex response, source filter, renderer, and tests to ship together. A partial update would route every brainstorm through the existing malformed-output failure path.
- New-feature ideas can become generic or speculative when repository evidence is weak. Continue requiring concrete repository-relative sources and rejecting ideas already represented in the checkout.
- The preferred `uv run` validation path cannot be exercised in the current environment because `uv` is unavailable; the equivalent `python3` targeted command was verified successfully.
