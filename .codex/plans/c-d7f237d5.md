# Codex plan for mehrangta/telegram_project_manager#55

Job: `c-d7f237d5` · Revision: 1

Fix the temporary manual brainstorm completion notifier by replying to the user’s original `/brainstorm` message instead of posting an unrelated message. The initiating message ID already flows from `BrainstormManager` through `BrainstormService.submit()` into `_run()`, but `_send_completion_notice()` currently discards it by passing `reply_to_message_id=None`. Preserve the existing five-second deletion, manual-only scope, topic routing, and best-effort failure behavior. No database, schema, configuration, or public command changes are required.

## Steps

1. **Preserve the notification reply target** — Extend `BrainstormService._send_completion_notice()` to accept `reply_to_message_id: int | None`. From `_run()`, pass the existing `reply_to_message_id` when a manual brainstorm succeeds. Forward that value to `_send()` rather than forcing it to `None`. This makes the temporary message a Telegram reply to the initiating command, which provides requester-targeted notification behavior in chats and topics. `BrainstormManager` already supplies `message.message_id`, so its interface and command behavior remain unchanged.
   - Likely files: `src/telegram_project_manager/bots/ideas/service.py`
2. **Keep completion delivery non-fatal** — Continue sending the completion notice only after the final brainstorm result has been delivered successfully and only when `trigger == "manual"`; scheduled runs already post a new result message and must not gain a duplicate notice. Preserve the helper’s exception isolation so notification send failures are logged but do not change the completed brainstorm’s `ok` database status or audit result. The Telegram API already uses `allow_sending_without_reply=True`, so a deleted or unavailable original command can fall back to posting the notice without failing the brainstorm.
   - Likely files: `src/telegram_project_manager/bots/ideas/service.py`, `src/telegram_project_manager/platform/telegram_bot.py`
3. **Preserve temporary-message lifecycle** — Keep tracking deletion tasks in `_notification_tasks`, sleeping for `completion_notice_seconds`, and deleting the exact returned completion-message ID. Preserve shutdown behavior: cancellation of the sleep should proceed directly to best-effort deletion before task cleanup. Continue treating an already-missing Telegram message as harmless and logging other deletion failures without altering the completed brainstorm status. No persistence or recovery mechanism is needed for these intentionally short-lived notices.
   - Likely files: `src/telegram_project_manager/bots/ideas/service.py`
4. **Correct and strengthen notifier tests** — Update the successful manual-run assertion so the second sent message targets the original command via `reply_to_message_id=40`, remains in topic `30`, and is deleted after the configured delay. Fix `test_incomplete_result_is_repaired_on_same_thread`, which currently fails because it still expects one sent message after the notifier feature added a second message; wait for notification cleanup and assert the same reply/delete behavior after a repaired successful response. Retain coverage proving scheduled runs send no extra notifier, notifier send/delete failures leave `last_status` as `ok`, and shutdown deletes pending notices. Add a compatibility assertion for `reply_to_message_id=None` if the helper remains nullable, confirming it still posts and cleans up without raising.
   - Likely files: `tests/test_brainstorm.py`
5. **Document and validate rollout** — Clarify that a successful manual brainstorm posts a temporary reply to the initiating command and removes it after five seconds, while scheduled runs remain unchanged. Deploy through the normal service update and restart path; there is no migration or feature flag. Validate both chat and forum-topic usage against Telegram because unit tests can verify reply parameters and deletion calls but cannot guarantee a client push notification when a user has disabled Telegram notifications.
   - Likely files: `src/telegram_project_manager/bots/ideas/README.md`

## Risks

- Telegram notification delivery ultimately depends on each user’s chat, topic, device, and reply-notification settings; replying to the initiating command supplies the correct Telegram relationship but cannot force a push notification.
- If the initiating command is deleted before completion, Telegram may send the notice without a visible reply relationship because `allow_sending_without_reply` is enabled; this is preferable to losing the completion notice or marking the brainstorm failed.
- The deletion task can race with service shutdown or a user manually deleting the notice. Existing cancellation and not-found handling should keep both cases harmless, but tests must continue waiting for `_notification_tasks` to settle.
- The focused fake bot verifies API arguments rather than Telegram client behavior, so manual end-to-end validation is required before considering the user-visible notifier fully verified.
- The repository’s current full-suite fallback stubs interfere across test modules and lack some Codex enum values; do not expand this issue into repairing unrelated test infrastructure.
